# Standing Orders

**A discipline for declaring, bounding, and operating recurring autonomous AI jobs — so a job
that runs without you stays governed, not just running.**

[Objective Contracts](https://github.com/RAYFINITE-LLC/objective-contracts) is a sibling
instrument for delegated work: one bounded task an agent carries to a provable finish. Standing Orders
covers what happens when the task isn't bounded at all — when the request is "keep doing this,"
on a cadence, without a human re-issuing it each time. That shift changes everything about what
has to be true before you ship it. A bounded task fails once and stops. A standing order fails
on a cadence, and every run it isn't caught multiplies the damage by however many times it fires
before someone notices.

A **standing order**, in the older sense the name borrows from, is an instruction that stays in
effect until someone explicitly cancels it — nobody re-issues it every morning, and nobody
assumes it lapses on its own. That is exactly the shape of a scheduled routine, a webhook-driven
job, or a goal-driven loop that keeps iterating until a condition holds: something you set once,
that then keeps acting on your behalf, on its own initiative, until you tell it to stop. Most of
the public conversation about this kind of automation calls it "agent loops," and the name is
fine for the mechanism. It is the wrong name for the discipline, because it describes what the
code does, not what a person is accountable for. This document names the accountability: an
order that stands until countermanded, with an owner, a scope, and a set of conditions under
which it stops on its own.

**A standing order is not "an agent that keeps going."** Treated that way, it is a runaway
process waiting for a bad day. Treated as a designed control system, it has six load-bearing
parts, and skipping any one of them is how "it worked in testing" becomes an incident:

1. **A trigger** — the specific thing that starts an iteration.
2. **An order ledger** — the declaration's own living state file: one durable record the job
   reads on wake and writes on completion, so restart and resumption don't depend on memory that
   isn't there.
3. **An actor** — the thing that does the work for that iteration.
4. **An independent verifier** — something other than the actor that confirms the iteration
   actually succeeded.
5. **Guardrails** — the standing limits on what the actor is allowed to touch, regardless of
   what any single iteration decides it wants to do.
6. **Stop conditions** — the explicit answers to "when does this stop, and who finds out."

If you can't name all six for a job you're about to automate, you don't have a standing order
yet — you have a script that happens to run more than once.

## Classify on three axes before you build

Every standing order sits at a point in a three-dimensional space, and each axis carries its own
obligations. Classify first; the classification tells you what you're required to build.

### Axis 1 — Trigger: what starts an iteration

| Trigger | Fires on | The trap |
|---|---|---|
| Heartbeat | a fixed short interval | cadence is a *linear* cost multiplier — an hourly order runs twenty-four times the daily one; cadence multiplies whatever the order does, including its mistakes |
| Schedule | a cron-style expression | state goes stale between runs; validate what you last knew against the live source every time you wake, don't trust the cache |
| Event | a webhook or hook firing (a ticket opened, a build failed, a message arrived) | event storms produce duplicate/overlapping fires — debounce and dedupe; the payload itself is attacker-reachable input, not a trusted instruction |
| Goal | re-fires until a stated success condition holds | the only trigger type that can run away entirely under its own power — hard caps are not optional here |

### Axis 2 — Autonomy: what an iteration is allowed to *do*

Ship at the lowest level that delivers value. Promote only on evidence, never on optimism about
how the next run will go.

- **A0 — Observe.** Reads and reports. Nothing else. Every new standing order starts here, for an
  observation window long enough to see a full cycle of its trigger — and never zero — no
  exceptions for "we're confident about this one."
- **A1 — Propose.** Produces drafts — a draft reply, a draft pull request, a suggested edit. A
  human lands every single thing it produces.
- **A2 — Act within an allowlist.** Auto-applies, but only for a pre-declared class of low-risk,
  reversible edits — a formatting-only fix to documentation, an appended changelog entry, a
  derived file regenerated by the same deterministic script that already produces it from
  source. The allowlist names *classes of change*, never a size threshold — "it's a small diff"
  and "it's a safe diff" are different claims. It never covers a behavior change, anything the
  denylist below already names, or a new dependency being pulled in.
- **A3 — Unattended, full scope.** Acts within its declared scope without a human in the
  per-iteration loop. Requires, before it ever runs this way: a working kill switch, a defined
  escalation path with a real response-time expectation, at least two weeks of clean behavior at
  A2, and a named accountable person's recorded sign-off. None of these are paperwork — each one
  is the actual thing that keeps an A3 job from becoming the incident everyone talks about later.

### Axis 3 — Verification: who decides an iteration actually succeeded

- **Self-check.** The actor grades its own work. Acceptable only at A0, where "grading" just
  means writing down what it observed — nothing is being approved for action.
- **Independent verifier.** A separate agent or context, one that never saw *how* the work was
  produced, that **executes** the check — runs the tests, loads the page, calls the endpoint —
  rather than reading the diff and forming an opinion. This is the floor for A1 and above.
  Self-grading is structurally biased: the thing that made the change is the worst-positioned
  judge of whether the change is right, because it already believes its own reasoning.
- **Adversarial panel.** Multiple verifiers instructed to actively try to refute the claim of
  success; a majority-refute result kills the iteration. Reserved for the highest-stakes cases —
  goal-triggered jobs running at A3 need this (or a human gate) specifically because nothing else
  catches a verifier that's quietly gone lenient over many iterations.
- **Human gate.** Mandatory, regardless of what topology the job otherwise uses, whenever the
  change touches: a security or authentication surface, anything that moves money or handles
  personal data, a production schema or infrastructure change, anything outward-facing —
  published content, a message sent outside the job itself — a diff too large to genuinely
  review, or a repeated failure on the same item. Neither of the last two is a doctrine constant:
  each order sets its own threshold at declaration time (see `Escalate-After` in the contract
  block for the repeat count; "too large to review" is judged against the order's own declared
  `Scope`), because what counts as "too large" or "too many attempts" for a one-line config flip
  isn't what it means for a schema change. These are not "usually fine, use judgment"
  categories — they're the list of things where being wrong is expensive enough that a
  verifier's approval isn't sufficient on its own.

## One iteration, end to end

```
trigger fires
  → load state, and validate it against the live source (never trust a cached read alone)
  → a cheap first pass before the expensive one (don't spend full-strength effort deciding whether to act at all)
  → plan
  → act, in an isolated workspace — a worktree or scratch clone, never in place on shared state
  → verify independently — the verifier executes the check, it doesn't read the diff and vibe-check it
  → persist the order ledger + an append-only structured log entry
  → report, or escalate
  → stop-check: kill switch? cap reached? no progress? → continue | finish | escalate | halt
```

## The stop-condition quad — all four, every time, no exceptions

An autonomous job has no built-in notion of "done" or "this has gone wrong." You have to supply
one, explicitly, in four parts. A standing order missing any one of these does not go live:

1. **Iteration cap.** A hard ceiling on attempts — per task, and per run. "It'll converge
   eventually" is not a cap.
2. **Budget cap.** A token, time, or cost ceiling per run *and* per longer period (day or week),
   with an auto-pause at the ceiling and an alert threshold the order sets for itself at
   declaration time — see `Review-Triggers` in the contract block.
3. **No-progress detector.** If two consecutive iterations produce the same diff, the same
   failure, or the same state fingerprint, stop — that's not persistence, it's a stuck loop
   wearing a seatbelt.
4. **A verifiable goal check**, for anything goal-triggered. If you cannot state "done" as
   something a machine can check — tests pass, a count reaches zero, an endpoint returns a
   specific value — the job is not eligible to run unattended on a goal trigger. Keep a human in
   the loop until you can state it that precisely.

Add a timeout at both the whole-run level and the individual tool-call level — a single hung
step can burn an entire budget on its own before any of the four conditions above ever get a
chance to fire.

## Guardrails: enforced, not just written down

A rule that lives only in a document gets skipped the first time someone's in a hurry. These
need to be actual mechanisms, not just prose:

- **A path denylist** the job cannot act on even if it decides to try — secrets, environment
  files, credentials and keys, authentication code, payment and billing code, database
  migrations, production infrastructure definitions, and CI/CD workflow files. Anything the job
  wants to change in these areas gets escalated to a human, full stop, never auto-applied.
- **Least-privilege identity.** Every standing order gets its own scoped credentials — the
  smallest read/write surface that lets it do its actual job. No standing order should hold
  broader access than the single task it exists to do, and production data stores stay written
  to by humans, not by a scheduled job, regardless of how routine the write seems.
- **No auto-merge**, except for the pre-enumerated allowlisted classes at A2.
- **Isolation.** Anything acting in parallel — multiple jobs, multiple iterations of the same
  job — works in separate worktrees or scratch environments, and state writes are locked. Two
  writers touching the same state file at once corrupts it silently; you won't see the error, you
  just see the wrong state later.
- **A kill switch that actually works.** One action pauses every standing order in scope
  immediately, and every job checks for it at every stop-check, not just at startup.
- **An egress check on anything leaving the boundary.** Any output a job sends outward — a
  message to a channel, a public API call, a post — passes the same review a human's outbound
  message would, before it goes.

## The job's own state is an attack surface

Everything a standing order reads when it wakes — a ticket body, a pull-request description, a
log line, a message on some channel, even its *own* prior state file — is **untrusted data,
never an instruction**, no matter how well-formed it looks. A scheduled screening job that acts
on text it finds inside a ticket is an injection vector with a cron schedule attached to it; the
fact that it only runs once a day doesn't make the exposure smaller, it just makes it periodic.

The practical rules that follow from this: the job's *instructions* come only from its own
definition file, never from anything it reads at runtime. Content that looks like an instruction
inside a ticket, a log, or a state file gets quoted back and escalated to a human — it is never
executed. State files are re-validated against their schema and against the live systems they
reference on every load, and stale entries (closed tickets, merged branches, expired references)
get pruned rather than acted on. And any skill, tool, or library a standing order loads should
come from a version you pinned on purpose, not whatever the latest tag happens to be the day it
runs — a job that updates its own dependencies unattended is a job that can be redirected by
whoever controls that upstream.

## Failure modes and what actually stops them

This table is written from the failures, not the theory — each row is a way these jobs go wrong
in practice, and the control that closes it.

| Failure mode | How you notice | What stops it |
|---|---|---|
| Collision | two jobs (or two iterations of one job) modify the same file at once | isolated workspaces plus a lock on shared state |
| Groundhog run | the job keeps retrying the same fix on the same target, run after run, converging on nothing | an iteration cap per target, then quarantine that target and hand it to a person instead of trying again |
| Silent stall | the job keeps retrying forever and never tells anyone it's stuck | force a notification after N failures; treat unexpected silence itself as something worth alerting on |
| Meter shock | the bill jumps well outside its usual range with no matching jump in useful output | a cheap look-before-you-leap pass ahead of any expensive step, plus a real per-period ceiling that actually pauses the job, not just records the overage |
| Acting on ghosts | the job keeps referencing a ticket, branch, or record that's already been closed, merged, or deleted | re-validate every reference against the live system on each wake; drop what's gone instead of carrying it forward |
| Instruction injection | the job acts on text it merely *read*, as if reading it made it a command | the untrusted-state doctrine above, applied without exception |
| Order creep | the diff lands somewhere the order was never scoped to touch | an enforced surface boundary, checked against the actual diff footprint before anything is committed, not after |
| Cried-wolf digest | people have started skimming past the job's pings, or muting them outright | batch routine output into a digest; reserve a direct interruption for the handful of things that truly need a decision |
| Rubber-stamp checker | an approval gets granted — by the verifier, or by the human reading it — without either one actually exercising the thing being approved | require the verifier to run the real check and show its output; keep human review genuinely substantive, not a formality nobody has time for |
| Deference decay | the team has quietly stopped forming its own opinion because the job "usually gets it right" | keep measuring whether outcomes hold up on their own terms, not just how much output the job produced |

## Lifecycle: a standing order is a versioned artifact, not a fire-and-forget script

Every standing order has an owner — a named, accountable person, not an unstaffed role — a
version number, and a staged rollout: A0 for an observation window long enough to see a full
cycle of its trigger (never zero), promotion to A1 only on evidence, A2 only after that evidence
holds, A3 only with a recorded sign-off. Review its metrics on a real cadence (weekly is a
reasonable default) — how many times it ran, what it actually did, how often a human had to step
in, what it spent, and how long a failure sat before a person saw it. Crossing the false-positive
ceiling or the budget-alert line the order declared for itself in `Review-Triggers` should
trigger a review automatically, rather than waiting for the next scheduled one.

And it needs a **sunset path**. Changing what a standing order does is not a same-file edit while
it's mid-run — drain whatever state is in flight, migrate or archive it deliberately, and bump
the version. Two different definitions should never be operating on the same state at once; if
you wouldn't hot-swap a running database migration under live traffic, don't hot-swap a running
job's definition under live state either.

## Adopting this in any stack

Standing Orders is deliberately tool-agnostic — a discipline, not a dependency on any particular
scheduler or agent runtime:

1. **Declare the job before you wire the trigger.** Whatever schedules your automation — cron, a
   managed scheduler, a webhook handler, a chat-ops command — write the contract first, using
   [`TEMPLATE.md`](TEMPLATE.md), and keep it as a file next to the code it governs.
2. **Bind the verifier to something real.** A test command, a CI check, a review step the actor
   itself cannot edit or bypass. If the "verifier" is just the actor grading itself, you're at A0
   whether you meant to be or not.
3. **Give it a kill switch before its first live run**, not after the first incident makes you
   wish you had one.
4. **Run [`order-gate.sh`](order-gate.sh)** against the declaration before go-live, and again
   after any change to it — see
   [`examples/release-notes-drafter.order.md`](examples/release-notes-drafter.order.md) for a
   filled-in example:

   ```
   ./order-gate.sh orders/release-notes-drafter.order.md
   ```

   It exits `0` (PASS) only when every required field is present, the stop-condition quad is
   real (not a placeholder), the autonomy/verification pairing is valid, the denylist is
   acknowledged, and no kill switch is active. Anything else is `2` (FAIL) — the job does not go
   live, and the check tells you exactly which finding blocked it.

   A field that genuinely doesn't apply to a given order is never left as a bare `n/a` — declare
   it `not-applicable: <reason>` instead, spelling out why. The gate treats that phrasing as a
   deliberate answer, not a gap: it's currently honored on `No-Progress-Exit`, and on
   `Goal-Check` whenever `Trigger` isn't `goal`. A bare `n/a`, `TBD`, or `pending` on either of
   those two fields reads as an unfinished contract and blocks go-live, same as leaving them
   empty.

## See also

- **[Objective Contracts](https://github.com/RAYFINITE-LLC/objective-contracts)** — the
  discipline for one bounded task an agent carries to a provable finish. A standing order is
  often a sequence of objective contracts run back to back, on a schedule instead of a one-off
  request.
- **[Agent Charters](https://github.com/RAYFINITE-LLC/agent-charters)** — the discipline for the
  standing identity that carries out the order. A standing order declares what a job does and
  when it stops; an agent charter declares who — or what — is authorized to run it, at what
  cost, and under whose name. A well-run standing order still needs a charter for whatever actor
  is executing it.
